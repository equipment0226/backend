# 실행 환경과 확인 기록

고객 화면, 사무소 화면, 사건을 처리하는 서버가 함께 실행돼야 전체 과정을 사용할 수 있습니다. 개인정보가 포함된 자료를 읽고 검토하는 AI도 내부 환경에서 사용할 수 있어야 합니다.

현재 작업 폴더의 로컬 실행 환경과 GitHub의 분리 저장소는 같은 기능을 제공하지만 실행 방법이 다릅니다. 아래에서 사용하는 환경에 맞는 안내를 확인하면 됩니다.

## 지금 작업 중인 PC에서 사용하기

현재 통합 작업 폴더에서는 `start-local.cmd`로 실행합니다. 고객 화면은 http://localhost:5173, 직원·변호사 화면은 http://localhost:5174 입니다. 실행 중인 서버가 있으면 같은 서버를 중복 실행하지 않습니다.

2026년 10월 4일 초기화 때는 기존 사건을 백업 후 비우고 계정을 보존했습니다. 이후 사용자가 직접 신청한 사건은 그대로 유지합니다. 초기화 기록의 사건 0건은 당시 상태이며, 지금 진행하는 사건 수는 화면의 사건 목록에서 확인합니다. 재시작해도 과거 시연 사건을 다시 만들지 않습니다.

접속 계정과 신청 순서는 [테스트 안내](testing.md)에 있습니다. 예전 검사 보고서에 남아 있는 사건 수나 화면은 당시 기록이므로 현재 사건 목록과 구분해서 봐야 합니다.

## 기능별로 필요한 준비

| 사용하려는 기능 | 필요한 준비 | 준비가 안 됐을 때 |
| --- | --- | --- |
| 로그인·상담·자료 제출 | 사건 서버와 해당 역할의 화면 | 접속 또는 저장을 할 수 없습니다. |
| 스캔·사진에서 글자 읽기 | 한국어 문서 판독 도구 | 판독 준비가 필요하다는 상태를 확인하고 자료를 다시 검토합니다. |
| 원문을 포함한 AI 검토·작성 | 내부 AI 서비스 | 확인된 사실은 보존하고 AI 확인이 필요한 부분을 남깁니다. |
| 익명 사건 정보의 심화 검토 | 서버의 외부 AI 연결 설정 | 외부 검토 결과를 얻지 못했다는 사유를 남깁니다. |
| 법률 근거 검색 | 수집한 공식 본문과 적용 기준 | 근거가 확보되지 않은 부분은 추가 확인이 필요합니다. |
| 한글 PDF 출력 | 한국어 글꼴과 원본 법원 서식 | 글꼴·서식 준비 상태를 확인해야 합니다. |

AI가 응답하는 데 시간이 걸릴 수 있어 화면에는 처리 중인 단계와 사유를 남깁니다. 응답 시간을 늘리는 설정만으로 문장의 정확성이나 처리 성공을 보장하지는 않습니다.

원문 대조는 확인할 분량에 맞춰 각 요청의 처리 시간을 배정합니다. 한 묶음이 시간을 넘기면 그 묶음만 더 작게 나누어 한 번 다시 확인합니다. 그래도 확인되지 않으면 이유를 남기고 다음 작성을 기다립니다. 이미 끝낸 대조는 원문과 검증 기준이 동일한 경우 일정 시간 이어서 사용할 수 있습니다. 이 임시 결과는 실행 중인 서버에 보관하므로 서버를 재시작하면 일부 대조를 다시 진행할 수 있습니다.

## 내부 AI가 GPU를 사용하는 방식

현재 테스트 PC에서는 문서 원문을 외부로 보내지 않고, PC의 GPU와 CPU가 나누어 읽고 대조합니다. Radeon 840M과 메모리 16GB 환경에서 모델 전체를 GPU에 올리면 메모리 부족으로 종료됐습니다. CPU가 맡을 내용은 일반 메모리에 두고, 33개 연산 층 가운데 16개를 GPU에 올리는 방식으로 실제 응답을 확인했습니다. 이때 GPU 사용 메모리는 약 2.8GB입니다. 모든 연산을 GPU에서 처리한다는 의미는 아닙니다.

GPU가 목록에 보이거나 서버가 응답하는 것만으로 준비 완료라고 판단하지 않습니다. 사건과 관계없는 가상 급여·채무 금액을 읽고, 기재되지 않은 금액을 미상으로 남기는지 확인한 뒤 해당 모델의 GPU 메모리 사용도 대조합니다. CPU로만 실행되거나 응답 검증에 실패하면 기동 확인을 통과하지 못합니다. 준비 상태를 다시 확인할 때는 이미 사용 중인 GPU 모델을 재시작하지 않습니다.

한 번에 모델 하나와 요청 하나만 처리하고, 이전 프롬프트를 보관하는 공간도 제한했습니다. 여러 문서를 계속 대조하는 동안 메모리가 불필요하게 늘어나는 것을 줄이기 위한 설정입니다. 처리 속도와 완료 시간은 문서의 길이와 PC의 다른 작업에 따라 달라집니다.

2026년 10월 4일 GPU 전환에서는 사건 DB를 별도 보관하고, 사건 서버를 유지한 채 AI 실행기만 같은 주소에서 교체했습니다. 이렇게 하면 원문과 검증 기준이 같은 완료 묶음을 이어서 사용할 수 있습니다. 실행기·기동 설정과 확인 방법은 [운영 환경 준비](deployment.md)에 정리했습니다.

## 이번 변경에서 무엇을 확인했나요?

새 박지우 가상 사례의 원본 자료 29종·53쪽을 읽었습니다. 문서별 기대 항목 78개와 사건 정보 36개를 대조했고, 추출한 461개 항목이 7종 작성 서식과 근거별지에 보존되는지 확인했습니다. DOCX·HTML도 내용을 대조했습니다. 원본의 은행 거래 168행과 대출 납입 36행을 포함한 검산 621개도 통과했습니다.

추가로 법률 판단이 필요한 입력을 명시적인 가상 예시로 넣어 계산 후 서식 연결을 시험했습니다. 이 범위에서 등록된 필수 작성 칸의 누락은 0개였습니다. 이 예시는 실제 사건에 저장하지 않았고, AI 검토나 제출 승인으로 표시하지 않았습니다. 새 자료는 글자가 포함된 PDF이므로 흐릿한 스캔의 판독 성능을 입증하는 시험은 아닙니다.

실제 AI 작성에서는 예금 금액을 생활비처럼 다루는 오류가 발견됐습니다. 금액의 의미까지 검사하도록 보완했고, 검증을 통과하지 못한 결과는 사실 요약과 보완 목록으로 남겼습니다. PDF 내용 보존 검사가 통과했다는 것과 AI 작성 문장이 모두 승인됐다는 것은 서로 다른 결과입니다.

회귀 검사는 사건 DB와 분리된 환경에서 실행합니다. 서류 한 건을 검토하면 그 자료의 값들이 함께 확인되는지, 개별 수정이 계산·문서에 유지되는지, 페이지 판독이나 AI 대조가 미완료일 때 다음 작성을 막는지 포함합니다. 검사 개수와 실행 시각은 아래 기록에서 확인할 수 있습니다.

검토를 마쳤는데 쟁점 분석으로 넘어가지 않는 경우에는 개요의 현재 처리 단계를 먼저 확인합니다. 직원의 서류 검토 이후에도 추출한 값과 원문의 AI 대조가 진행될 수 있습니다. 긴 원본은 해당 값의 페이지·인용문과 단위·기간 근거를 함께 나누어 확인하고, 여러 서류에 등장한 같은 값은 연결된 원문을 모두 대조합니다. 처리한 묶음 수와 대기 사유를 표시하며, 확인이 끝나지 않은 값을 완료로 간주해 다음 작성을 시작하지 않습니다.

이후 단계의 연결도 실제 사건을 변경하지 않는 복제 환경에서 확인했습니다. 시험용 AI 판정을 사용해 원문 대조가 끝난 상황을 만든 뒤, 실제 추출값이 계산·전략 구성·7종 PDF 작성까지 전달되는지 살폈습니다. 확인되지 않은 판단은 보완 항목으로 남고 제출 승인은 되지 않습니다. 이 검사는 단계 간 연결과 문서 출력을 확인한 것이며, 실제 AI 판단의 정확성이나 모든 작성 칸이 완비됐다는 의미는 아닙니다.

ZIP 접수는 파일명을 무작위로 바꾼 PDF 29개를 실제 비동기 처리 경로에 넣어 확인했습니다. 요청 연결, 원본 내용 보존, 추출 완료 기록과 검토 전 상태를 대조했습니다. 분류에 외부 AI를 호출하지 않았으며, 이 결과를 모든 스캔·기관 서식에 대한 정확도로 해석하지 않습니다.

개요와 법률쟁점은 같은 계산·증빙·공개 근거를 사용하는지 확인했습니다. 공식 법률·법원 자료 10건의 본문을 다시 수집했고, 별도의 가상 사건을 익명화해 실제 심화 검토도 호출했습니다. 이 검토는 의도적으로 넣은 채무 금액의 불일치를 보완 대상으로 남겼으며, 인가나 문서 승인을 받은 결과는 아닙니다.

## 확인 기록을 찾아보려면

다음 파일은 로컬 검사 결과입니다. 고객 자료와 실행 흔적이 저장소에 섞이지 않도록 Git에는 포함하지 않습니다.

| 확인할 내용 | 로컬 기록 위치 |
| --- | --- |
| 새 서류 추출과 사건 정보 대조 | `reports/court-ready-fixture/extraction.json` |
| 작성 문서의 내용 연결 | `reports/ocr-audit/court_ready_fixture-generated-documents.json` |
| 가상 판단을 넣은 계산·서식 연결 | `reports/court-ready-fixture/reviewed-layout.json` |
| 원본 금액 검산과 시각 확인 | `reports/court-ready-fixture/arithmetic.json`, `source-visual-review.json` |
| 세 계정 로그인·사건 0건 시작 | `reports/browser-fresh-start.json` |
| 가상 사건 정리·백업 | `reports/test-case-reset.json` |
| 대시보드·법률쟁점 화면 | `reports/case-dashboard/result.json` |
| 뒤로·앞으로 이동, 상세 주소, 목록 위치 복원 | `reports/navigation-history/result.json` |
| 복수 원본·ZIP 제출 화면 | `reports/upload-batch/result.json`, `reports/archive-upload/result.json` |
| 실제 익명 심화 검토 | `reports/dashboard-real-review.json` |
| 내부 AI의 합성 금액 대조와 GPU 사용 | `reports/local-gpu-check.json` |
| 최신 회귀 검사 | `reports/test-results.json` |
| 독립 실행·파일 일치 확인 | `.work/repository-split/validation.json` |
| 세 저장소 업로드 확인 | `reports/git-publication.json` |

`reports/test-results.json`은 해당 작업 폴더에서 마지막으로 실행한 검사 기록입니다. 분리 저장소에서 실행한 검사는 시점이 다를 수 있습니다. 가상 응답으로 검사한 기능과 실제 AI를 호출해 확인한 기능도 나눠 해석해야 합니다.

## 설치 담당자 참고

Python 의존성과 한국어 판독 설치는 각 저장소 README 및 [서류 읽기 안내](ocr.md)를 따릅니다. 통합 작업 폴더의 실행기는 로컬 환경 파일을 읽지만, 분리 저장소의 직접 실행은 운영체제나 배포 환경에 설정을 전달해야 합니다.

환경 파일에는 실제 키가 있을 수 있으므로 문서나 Git에 내용을 복사하지 않습니다. 사건 데이터가 들어 있는 `.local`도 임시 파일처럼 지우지 않습니다. 보관과 복원은 [운영 환경 준비](deployment.md)를 참고하세요.
