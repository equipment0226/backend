# 상담에서 1차 작성·보완·제출 기록까지

고객의 상담 신청을 받으면 담당자가 세부 상담을 요청하고 상담 내용을 기록합니다. 이후 필요한 서류를 정해 고객에게 요청하고, 제출 자료의 검토가 완료되면 **자료 정리부터 1차 문서 작성과 AI 문서 검토까지 자동으로 진행**합니다. 담당자는 진행 이력을 확인하면서 부족한 자료와 판단이 필요한 부분에 집중할 수 있습니다.

자동 작성이 끝나면 담당자 보완과 변호사 최종 승인을 기다립니다. 문서가 생성됐다는 이유만으로 제출 가능한 상태나 법원의 인가로 표시하지 않습니다.

## 업무가 이어지는 순서

| 단계 | 처리하는 내용 | 문제가 있으면 |
| --- | --- | --- |
| 세부 상담 | 신청 내용은 보존하고, 담당자가 요청한 상세 상담을 별도로 기록 | 상담이 완료될 때까지 추출을 시작하지 않음 |
| 필요서류 선정·제출 확인 | 상담 내용과 관할 기준으로 기관·계좌·기간별 요청을 구성 | 고객에게 필요한 자료 안내, 불필요해진 요청 철회 |
| 서류 범위·내용 검증 | 명의·종류·기간·발급 옵션과 요청 범위를 확인 | 부족하거나 잘못된 자료를 구분해 재요청 |
| 추출값 원문 대조 | 글자·금액·항목의 원문 위치와 단위·기간을 확인 | 불명확한 항목은 확인 필요 상태로 유지 |
| 쟁점·전략·법률계산 | 확인된 사실을 계산하고 관련 기준·사례와 함께 검토 | 미확정 계산과 법률 판단의 보완 사유를 정리 |
| 1차 문서 자동 작성 | 확인된 사실을 편집용 문서와 공식 서식에 반영 | 작성 가능한 내용은 보존하고 부족한 부분은 공란·보완 목록으로 표시 |
| AI 문서 검토 | 문장·금액 의미, 출력된 값, 원본 서식의 적용 범위를 대조 | 발견한 오류와 검토하지 못한 범위를 담당자에게 전달 |
| 담당자 보완·최종 승인 | 원문과 초안을 대조하고 수정본을 다시 검토한 뒤 변호사가 승인 | 수정·추가 자료 반영 후 재작성·재검토 |
| 제출 처리 | 외부 제출 후 접수증과 사건번호를 확인해 내부 제출 이력 저장 | 접수 근거나 승인된 문서와의 일치 여부를 확인 |

세부 상담은 자동 처리의 출발 조건이며, 그 이후 여덟 단계의 진행 이력을 남깁니다. 고객의 최초 신청 문구를 담당자의 완료된 상담으로 취급하지 않습니다. 완료된 상담을 수정하거나 자료를 추가하면 최신 내용을 기준으로 다시 처리합니다.

## 자료가 모인 뒤의 1차 초안 작성

서류가 아직 도착하지 않았거나 다른 사람의 자료가 섞여 있으면 수집·명의 확인을 먼저 해결합니다. 그러나 자료 제출과 검토가 완료된 뒤의 AI 검토 불확실성이나 미확정 계산 때문에 확인된 사실까지 모두 지우지는 않습니다.

예를 들어 급여명세의 월 실수령액, 부채증명의 원금과 이자, 계좌 잔액은 원문과 단위·기간·집계 근거를 대조해 1차 초안에 담습니다. 생계비 인정인원·면제재산·비용·최종 변제액 등 미확정 판단은 별도로 남깁니다. 기준에 따른 검토용 제안이 있더라도 확정값과 구분합니다.

AI가 응답하지 않거나 문장 검토를 통과하지 못하면 해당 사유를 기록합니다. 가능한 경우에는 원문에서 확인한 사실을 정리한 본문을 남기며, 설득력 있는 최종 진술이 완성됐다고 표시하지 않습니다. 검토가 끝나지 않은 이전 단계도 완료로 바꾸지 않습니다.

진행 화면에는 현재 단계와 처리한 묶음 수가 표시됩니다. 자료가 바뀌어 다시 처리할 내용이 생기면 현재 작업과 최신 자료 대기를 구분합니다. 기존 결과는 자료와 적용 기준이 여전히 같은 경우에만 재사용합니다.

## AI 검토와 사람의 승인

AI 문서 검토는 작성된 내용이 원문과 맞는지 확인하는 과정입니다. 예금 잔액을 생활비라고 썼는지, 월소득과 연소득이 바뀌었는지, 인용이 실제 근거를 뒷받침하는지 등을 대조합니다. 문장 검증에 성공했더라도 실제 PDF의 값·빈칸·배치와 원본 선택 문구는 별도로 확인합니다. 생성된 문서 자체를 사실의 근거로 사용하지 않습니다.

직원·변호사 화면의 **작성 내용·AI 검토 확인**에서 실제 작성값, 출처, 발견사항, 검토하지 못한 범위를 볼 수 있습니다. 잘못된 내용은 원문이나 입력을 보완한 뒤 **새 버전 작성**, **AI 문서 재검토**로 이어갑니다. 기존 PDF와 검토 이력은 보존합니다.

진술서 자동 작성은 상세 상담과 증빙을 근거로 세 문단을 작성하고 대조합니다. 의미상 오류에는 한 차례 수정을 허용하며 실패를 반복해 성공으로 포장하지 않습니다. 진술서만 별도로 새로 작성하는 화면에서는 검증 실패 시 작성 보류 사유를 안내합니다. 직원이 직접 수정 옵션을 명시적으로 선택한 경우에만 수동 입력을 받으며, 이 내용도 재검토 대상입니다. 전체 자동 진행의 사실 요약 초안과 이 별도 작성 절차는 구분합니다.

## 최종 승인과 제출 기록

문서·결과 화면의 **보완·최종 승인·제출 처리**에서 필요한 7종과 남은 보완 사유를 확인합니다. 제출 패키지를 준비하려면 현재 자료에 대한 필수 항목, 원문·계산 대조, 문서 검토, 미결 사실·쟁점·서류 요청 등을 해결해야 합니다. 1차 초안이 있다는 것만으로 이 조건을 충족하지 않습니다.

변호사는 서명·동의·별지·법원의 추가 요구까지 확인한 후 확인 항목과 사유를 남겨 최종 승인합니다. 승인 이후 원문, 계산, PDF 또는 적용 기준이 바뀌면 이전 승인으로 제출 처리할 수 없습니다.

실제 법원 전송은 이 시스템에서 수행하지 않습니다. 외부에서 제출한 뒤 접수증을 올리고 명의·사건번호·접수 사실을 확인해 내부 제출 기록을 남깁니다. 이 기록도 법원의 인가를 뜻하지 않습니다.

## 확인한 범위

두 가상사건의 자료를 각각 15종씩 처리해 7종 PDF를 각각 만들었습니다. 원문에서 확인한 항목은 119개·123개였으며 모두 원문 인용과 함께 보존되는지 확인했습니다. 편집용 문서의 주요 금액과 본문도 대조했습니다. AI 의미 검토를 사용할 수 없는 상황에서도 확인된 사실이 사라지지 않는 경로를 시험했습니다.

두 번째 실제 문장 작성 시험은 의미 검토 보완이 필요한 상태로 끝났습니다. 따라서 최종 감사에 사용한 본문은 확인된 사실 요약이며, 고급 진술 작성의 성공으로 보고하지 않습니다. 최종 PDF 35쪽의 시각 검토에서는 줄 겹침 수정을 확인했고, 미확정 계산칸과 일부 배치 한계도 기록했습니다.

이 검증은 가상자료의 처리·근거 보존·배치에 대한 확인입니다. 실제 법원 제출이나 인가, 모든 기관 서식의 정확도를 검증한 것은 아닙니다. 세부 결과는 [자료 추출](document-extraction.md), [원문 판독](ocr.md), [법원 서식 작성](court-forms.md)에서 확인할 수 있습니다.

## 운영·연동 참고

고객 원문을 다루는 판독·문서 검토는 로컬에서 처리합니다. 외부 AI의 심화 검토에는 고객 식별정보나 상담·서류의 원문을 보내지 않고, 허용한 수치와 분류 정보로 다시 정리해 전달합니다. 개인정보 처리 방식은 [검증 코드](../apps/api/verification.py)에서 확인할 수 있습니다.

주요 연동 경로는 다음과 같습니다. 모든 변경 요청에는 사건 권한과 최신 사건 버전 확인이 적용됩니다. 동시에 수정되어 충돌하면 새 사건 상태를 받은 뒤 다시 요청해야 합니다.

| 연동 기능 | 경로 |
| --- | --- |
| 서류 제출 | POST /api/cases/{id}/documents |
| 자동 처리 실행 | POST /api/cases/{id}/ax-runs |
| 계산·계산 승인 | POST /api/cases/{id}/legal-calculations, 해당 계산의 /approve |
| 원본 서식 목록·미리보기 | GET /api/court-forms, GET /api/court-forms/{template}/preview |
| 새 서식 작성·AI 재검토 | POST /api/cases/{id}/court-documents, 해당 문서의 /verify |
| 작성본 내려받기 | GET /api/cases/{id}/court-documents/{doc}/download |
| 제출 가능 조건 확인 | GET /api/cases/{id}/filing-readiness |
| 제출 패키지 준비·승인 | POST /api/cases/{id}/filing-packages, 해당 패키지의 /approve |
| 접수증 연결·제출 기록 | 해당 패키지의 /receipts, POST /api/cases/{id}/submissions |

접수증은 파일과 사건번호뿐 아니라 명의·사건번호·접수증 확인 및 사유가 필요합니다. 이 API를 호출한다고 외부 전송이 이루어지는 것은 아닙니다. 상세 조건은 [최종 승인·제출 처리](../apps/api/filing.py)와 [접수증 연동](../apps/api/filing_routes.py), 진행 단계는 [업무 단계 정의](../apps/api/workflow_contract.py)를 참고합니다.
