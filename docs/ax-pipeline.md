# 상담에서 변호사 검토까지: 로컬 AX 실행 흐름

이 문서는 상담 접수·기존 팩터·HTTP 연결 계약을 설명한다. 전체 자동 단계와 보류 조건은 [AX 자동화](ax-automation.md), 단계 정본은 `apps/api/workflow_contract.py`를 따른다.

현재 목표는 **상담 회의록을 사건으로 만들고, 상황에 필요한 자료를 정한 뒤, 제출자료의 값과 근거를 1차 서류에 연결해 변호사가 검토하게 하는 것**이다. 고객과 직원은 같은 사건 원장을 사용하고 각각 별도의 프론트엔드에 접근한다. 자동화의 중심은 백엔드이며 n8n은 이후 외부 이벤트와 실행 순서를 연결하는 계층으로 붙일 수 있다.

## 언제, 어떤 정보가, 어느 문서로 가는가

```mermaid
flowchart LR
    A[상담 회의록 입력·업로드] --> B[인물·지역·사건유형 후보]
    B --> C[조건별 업무 규칙]
    C --> D[필요서류·기간·이유]
    D --> E[고객 자료 제출]
    E --> F[인물·종류·기간·판독 상태 검사]
    F --> G[원문 인용이 있는 추출값]
    G --> H[자료 완비 후 계산·전략 분석 및 1차 작성]
    H --> I[AI 문서 재검토·담당자 보완·최종 승인]
    F --> J[누락·충돌·추가자료 질문]
    J --> E
    K[공식 원문 검색] --> C
    K --> F
    K --> H
```

| 발생 시점 | 입력 | 처리 및 남는 기록 | 다음 결과 |
| --- | --- | --- | --- |
| 직원이 회의록을 보냄 | 회의록 원문, 직원·조직 정보 | 내담자·지역·관할·유형 후보, 원문 인용, 분석 상태 | 사건, 상담 원문, 초기 필요서류 |
| 상담의 조건이 발견됨 | 급여·사업·주거·부양·완납 등 원문 표현 | 매칭한 `WF` 규칙, 해당 인용, 필요한 팩터 | 서류 종류·기간·요청 이유 |
| 파일이 도착함 | 파일 원본, 연결한 요청, 사건 버전 | SHA-256, 추출 본문·페이지, 명의·종류·기간·판독 검사 | 추출 후보, 불충분 사유, 자료 보완 후보 |
| 자동 분석이 완료됨 | 사건 스냅샷, 업무 규칙, 검색된 공식 원문 | 근거 검사·실행 상태·부족 자료 | 단계 조건 충족 시 새 작성본, 미충족 시 보완 요청 |
| 변호사가 검토함 | 초안, 출처, 누락·충돌, 현재 사건 버전 | 결정·이유·담당자·검토시각 | 검토 결과가 남은 초안 |
| 상담·증빙이 바뀜 | 새 자료와 새 버전 | 이전 제안·초안의 유효성 재검사 | 최신 자료로 재분석·새 초안 |

자동 추출값은 `candidate`다. 원문에 수치가 있다는 사실과 법률상 인정되는 사실은 다르다. 값이 없으면 `미확인`, 출처가 서로 다르면 `conflict`로 남긴다. 필수 자료 제출·검토가 완료되면 미확정 법률판단·독립 검증 항목을 공란·확인 목록으로 남긴 1차 작성본까지 자동 생성한다. 제출본 확정은 보완과 AI 재검토, 변호사 최종 승인을 거친다. 상세 화면에서는 후보·작성본·보완 사유와 이력을 계속 확인할 수 있다.

v2에서 보존한 [registry.json](../data/registry.json)의 **66개 팩터·34개 법률 규칙**은 참조 설계 등록부다. 위의 **29개 실행 팩터·18개 업무 규칙**과 같은 집합이 아니며, 66개를 모두 실행·법률 검증했다고 표시하지 않는다. 기존 등록부의 승인 전·비활성 상태는 보존한다. `WF`의 `source_refs`는 기존 규칙·요구사항 ID 연결이고, 다운로드 원문의 조문 인용은 별도의 corpus 청크로 추적한다.

예를 들어 “가족이 카드대금을 완납했다”면 완납 사실 하나로 채무를 지우지 않는다. `WF05`가 완납일, 지급자, 자금 원천, 가족 간 대여·증여·대위 관계, 남은 채무를 요청하고 부채증명·송금자료·약정과 연결한다. 확보한 값은 채권자목록과 진술서에 후보로 들어가며 법률관계의 최종 판단은 검토 항목으로 남는다.

## 공식 원문과 Llama의 역할

공식 공개 법률·법원 실무준칙·정부 안내를 수집한다. 수집 수치는 [legal-ingestion.json](../reports/legal-ingestion.json), 추가 판례는 [법률 연구 목록](../data/legal_research/manifest.json), 현재 반영 상태는 직원 지식함의 실제 원문·감시 상태에서 확인한다. 과거 수집 보고서의 실패 건수는 현재 상태를 대신하지 않는다.

| 구분 | 실제 확보한 범위 |
| --- | --- |
| 법률 | 채무자회생법 전체 본문과 관련 조문; 출처별 법령판·시행일·해시를 연결 |
| 법원 | 서울·수원·부산 실무준칙 PDF, 서울 개인회생·파산 안내 및 관할 안내 |
| 정부 안내 | 생활법령 신청서·첨부서류 작성 안내, 정부24 소득금액·건강보험 자격득실·주민등록 서비스 안내 |
| 수집 실패 | HTTP 200이어도 메뉴만 있는 본문은 실패 처리; 일부 조문은 같은 법령판의 확인된 전체 본문에서 재추출 |

원문 파일은 `.local/corpus/raw/`, 검색 스냅샷은 `.local/corpus/snapshot.json`에 있다. 각 청크는 URL, 수집시각, SHA-256, 조문·단락 또는 PDF 페이지, 법원, 문서종류를 가진다. 원본 PDF의 페이지와 인쇄쪽수는 다를 수 있다. 수원 PDF는 한 PDF 페이지에 좌우 인쇄면이 있는 구조라 좌우를 분리해 읽는다.

검색은 한국어 문자 bigram을 포함한 BM25다. 법원을 지정하면 해당 법원 자료와 전국 공통 자료만 반환한다. 개인회생 검색에서는 분류한 일반회생·국제도산·파산 부분의 혼입을 줄인다. 검색 결과와 본문 추출은 **현행성 검증, 전체 지방법원 규칙 반영, HWP 서식 지원, 법률 판단의 정확도**를 보장하지 않는다. 수집자료 변경만으로 승인 전 법률 규칙을 활성화하지 않는다.

로컬 Ollama의 `llama3:latest`는 사건 원문에서 팩터·문서 유형을 선택한다. v3 하네스는 모델이 원문 구간 ID를 선택하고 코드가 인용·금액을 읽도록 역할을 나눈다. 공식 근거 검색과 준비 규칙은 별도 단계에서 연결해 표시하며 모델의 법률 추론으로 표현하지 않는다. 원문에 없는 인용과 근거 없는 값은 반영하지 않는다. 실패·시간초과·규칙만 실행된 상태를 모델 성공과 구분한다. 모델 학습이나 의미 벡터 검색을 구현한 상태는 아니다. 현재 GPU 사용 여부는 실행 메트릭을 확인해야 하며 GPU 가속 성공으로 가정하지 않는다.

## 로컬에서 확인하기

1. 프로젝트 루트에서 `python scripts/dev.py`를 실행한다. 사무소 화면은 `http://localhost:5174`, 고객 화면은 `http://localhost:5173`, API 문서는 `http://localhost:8000/docs`다.
2. 사무소 시연 계정으로 합성 회의록을 입력한다. 예: “내담자는 홍길동입니다. 서울 마포구에 거주하고 개인회생을 상담합니다. 회사원이며 월 급여는 280만 원입니다. 월세 60만 원, 보증금 1,000만 원입니다. 최근 카드론을 받아 생활비로 썼습니다.”
3. 새 사건의 인물·지역·사건유형, `WF02/04/06` 등 매칭 근거, 필요한 자료와 미확인 팩터를 확인한다. 결과의 `model_status`와 실행시간도 함께 본다.
4. 이름·급여·기간이 적힌 **합성 자료**를 해당 자료 요청에 업로드한다. 자동 검사에서 인물·종류·기간 일치와 추출값을 확인한다. 다른 이름이나 다른 금액을 넣으면 충돌·검토 상태로 남는지 확인한다.
5. 모든 요청·원문 검증·계산·전략 조건이 충족된 경우 작성본의 출처·버전·검증 범위를 확인한다. 보류된 경우에는 보완 사유를 확인하고, 필요한 담당자 판단을 반영한다. 기존 변호사 검토 화면과 결정·이유 이력은 유지한다.
6. 자료를 바꿔 이전 제안·초안이 그대로 승인 대상에 남지 않는지 확인한다. 모델 서버를 끈 경우에도 원문과 자료 준비 작업이 남고 모델 실패가 표시되는지 확인한다.

공식 원문을 다시 수집하고 corpus 검증을 재실행하는 명령은 다음과 같다. 수집은 허용된 공식 공개 URL만 사용하며 사건 회의록·증빙은 요청에 포함하지 않는다.

```powershell
python scripts/ingest_legal.py
python -m unittest discover -s tests -p test_corpus.py -v
python -m unittest discover -s tests -p test_ax_pipeline.py -v
```

`test_ax_pipeline.py`는 실제 HTTP·SQLite·DOCX 흐름을 검사하되 모델 응답은 합성값으로 대체한다. 실제 Llama 성능 측정과 이 테스트의 성공 여부는 별개다.

## HTTP 경계와 버전

아래 경로는 공통 `/api` 아래 있다. 권한은 API가 검사한다. 외부 자동화도 직원에게 허용된 업무만 요청하며, 변호사 승인은 변호사 권한과 이유를 요구한다.

| 목적 | 메서드·경로 | 입력·응답의 핵심 |
| --- | --- | --- |
| 인증 | `POST /api/auth/login` | `username`, `password` → `token`; Bearer 인증 |
| 회의록 접수 | `POST /api/intake-runs` | `{ "text": "..." }` → `run_id`, `status` |
| 회의록 파일 | `POST /api/intake-runs/upload` | multipart 파일, 지원 형식·크기는 API 명세 확인 |
| 접수 진행 | `GET /api/intake-runs/{run_id}` | `status`, 완료 시 `result.case_id` |
| 사건 읽기 | `GET /api/cases/{case_id}` | 최신 `version`, 요청자료, 후보, 초안 |
| 자료 제출 | `POST /api/cases/{case_id}/documents` | multipart `file`, `request_id`, `expected_version`; 저장 후 자동 AX |
| 사건 분석 목록 | `GET /api/cases/{case_id}/ax-runs` | 실행별 상태·근거·결과 |
| 분석 진행 | `GET /api/ax-runs/{run_id}` | 완료·실패·만료를 구분 |
| 초안 내려받기 | `GET /api/cases/{case_id}/drafts/{draft_id}/download?format=docx` | 인증된 원문 다운로드 |
| 변호사 검토 | `POST /api/cases/{case_id}/drafts/{draft_id}/review` | `decision`: `approve` 또는 `request_changes`, `reason`, `expected_version` |

동일 사건 내용·지식·작업유형의 분석은 기존 실행을 재사용한다. 대기열과 동일자료 재시도 상한도 백엔드가 관리한다. 업로드는 같은 요청의 동일 파일 SHA-256을 중복으로 받지 않는다. 반면 **현재 회의록 신규 접수 POST는 영속적인 `Idempotency-Key` 계약이 없다.** 외부 이벤트를 재전송하면 새 사건이 생길 수 있으므로 이 POST에 무조건 자동 재시도를 켜지 않는다.

업로드나 검토의 409 응답은 현재 사건을 다시 읽고 변경 내용을 확인해야 한다는 뜻이다. `expected_version`만 최신으로 바꿔 같은 승인을 강행하지 않는다. 실행 시작 후 사건 또는 corpus가 바뀌면 과거 결과를 자동 적용하지 않는다.

## n8n으로 옮길 범위

[n8n-local-workflow.json](n8n-local-workflow.json)은 **회의록 Webhook 접수 → 백엔드 작업 생성/기존 작업 재조회 → 즉시 run_id 응답 → 상태 폴링 → 사건·초안 확인**의 가져오기용 예제다. JSON 구조·연결은 검사했으며 실제 n8n 인스턴스에서 가져오기·실행한 결과는 아니다. 외부 배포·이메일 발송·법원 제출 노드는 포함하지 않는다.

n8n의 Webhook은 테스트 URL과 운영 URL을 구분하며 인증을 설정할 수 있다. 이 예제는 비활성 상태이며 Header Auth를 선택하도록 했다. [공식 Webhook 문서](https://docs.n8n.io/integrations/builtin/core-nodes/n8n-nodes-base.webhook/)

HTTP Request 노드는 API 호출과 인증을 맡고, Respond to Webhook 노드는 작업 ID를 202 응답으로 돌려준다. 백엔드 분석이 끝날 때까지 요청 연결을 유지하지 않는다. [HTTP Request](https://docs.n8n.io/integrations/builtin/core-nodes/n8n-nodes-base.httprequest/), [Respond to Webhook](https://docs.n8n.io/integrations/builtin/core-nodes/n8n-nodes-base.respondtowebhook/)

Wait와 If 노드는 10초 간격으로 `queued/running` 여부를 확인한다. 예제는 6분이 지나면 폴링을 멈추고 현재 상태를 남기며 백엔드 작업을 취소하지 않는다. [Wait](https://docs.n8n.io/integrations/builtin/core-nodes/n8n-nodes-base.wait/), [If](https://docs.n8n.io/integrations/builtin/core-nodes/n8n-nodes-base.if/)

가져오기와 로컬 설정:

1. n8n의 **Import from File**로 JSON을 가져온다. 파일에는 자격증명 값이 없다. [공식 가져오기 안내](https://docs.n8n.io/workflows/export-import/)
2. 로컬 테스트는 백엔드와 같은 PC의 n8n에서 시작한다. 기본 API 주소는 `http://127.0.0.1:8000`이다. Docker의 `127.0.0.1`은 컨테이너 자신이므로 같은 주소로 호스트 API에 접근할 수 없고, 기본 데모 API도 외부 접속을 차단한다. 컨테이너·PaaS 이식 시 실행망과 인증 구성을 별도로 정한다.
3. Webhook에 Header Auth 자격증명을 선택한다. HTTP Request 노드 세 곳에는 `Authorization` / `Bearer <직원 로그인 토큰>`을 n8n Credentials로 등록한다. API 로그인 토큰은 8시간 후 만료된다. 실제 토큰을 이 문서·JSON·저장소에 넣지 않는다. [HTTP 인증 문서](https://docs.n8n.io/integrations/builtin/credentials/httprequest/)
4. **Listen for test event** 후 테스트 URL에 `{ "text": "합성 상담 원문..." }`을 보낸다. 반환한 `run_id`를 호출 측에서 저장한다. 다시 상태만 확인할 때는 `{ "existing_run_id": "intake-..." }`로 보내 신규 접수를 건너뛴다.
5. `Review ready` 결과의 사건·초안 ID를 사무소 UI에서 확인한다. 초안 검토는 n8n이 자동 승인하지 않는다.

추후 외부 업로드 이벤트를 붙일 때는 `case_id`, `request_id`, 현재 `expected_version`을 구한 뒤 HTTP Request의 multipart로 자료를 전달한다. 백엔드가 이미 자동 AX를 시작하므로 같은 업로드에 별도 분석 시작 POST를 중복 호출할 필요가 없다. n8n은 분석 목록·실행 상태를 조회해 다음 단계만 연결하면 된다.

실서비스의 재시도는 `external_event_id → run_id/case_id` 대응을 영속 저장하고, 백엔드가 조직·이벤트 종류·내용 해시에 대한 idempotency 키를 원자적으로 처리하도록 확장한 뒤 활성화한다. 네트워크 시간초과는 처리 실패를 뜻하지 않으므로 작업 ID를 먼저 조회한다. 실패한 모델 호출을 n8n이 무제한 반복하지 않는다.

원문 저장, 조직·사건별 접근권한, 인용 검사, 추출 후보의 상태, 규칙 버전, 지식 스냅샷, 사건 버전 충돌, 초안 생성·검토·감사 기록은 백엔드에 유지한다. n8n은 SQLite를 직접 수정하거나 프롬프트 판단만으로 초안을 승인하지 않는다. 이 경계를 유지하면 n8n 교체·중단 시에도 사무소와 고객 UI의 같은 사건 원장을 계속 사용할 수 있다.
