# 처음부터 직접 테스트하기

2026년 10월 4일 로컬 테스트 환경을 **계정 3개, 사건 0건**에서 시작하도록 정리했습니다. 이후 고객이 직접 신청하면 직원·변호사 화면에 같은 사건이 연결됩니다. 새 수동 테스트에는 가상 고객 **이하늘**의 상담 예시와 서류 15종을 사용합니다. 이전 김새봄 자료는 자동 검사 비교용으로 보존합니다.

## 접속과 계정

| 화면 | 주소 | 아이디 | 비밀번호 |
| --- | --- | --- | --- |
| 고객 | http://localhost:5173 | customer | customer |
| 직원 | http://localhost:5174 | staff | staff |
| 변호사 | http://localhost:5174 | lawyer | lawyer |

직원과 변호사를 함께 확인하려면 서로 다른 브라우저나 브라우저 프로필을 사용하세요. 서버가 꺼져 있다면 프로젝트의 `start-local.cmd`를 실행합니다. 자동 판독·검토를 이용하려면 로컬 AI 서비스도 실행되어 있어야 합니다. 위 계정은 로컬 테스트용입니다.

## 1. 고객이 상담 신청하기

고객으로 로그인하고 **내 사건 → 상담·신청 시작 → 가상 상담 예시 불러오기**를 선택합니다. 이하늘의 이름, 서울회생법원, 상담 내용이 채워집니다. 이 버튼은 입력만 채우므로 내용을 확인하고 직접 동의·신청해야 사건이 생깁니다.

신청 직후에는 담당자의 세부상담 안내를 기다립니다. 아직 자동 추출이나 서류 요청을 시작하지 않는 것이 정상입니다.

## 2. 직원이 세부상담 기록하기

직원으로 로그인하여 새 신청 알림이나 사건 목록에서 이하늘 사건을 엽니다. **상담 기록**에서 고객이 남긴 신청을 확인하고 **세부 상담 요청**을 보냅니다. 고객 계정의 알림과 **담당자 문의**에 안내가 도착하는지 확인합니다.

고객 답변이나 통화에서 확인한 내용을 담당자가 질문별 답변과 종합 기록에 정리합니다. 가상 테스트에서는 제공된 상담 예시의 사실관계를 사용합니다. 자료 활용 동의를 확인하고 **상담 완료·추출 시작**을 누르면 이 기록을 기준으로 필요한 서류를 선정합니다.

## 3. 고객이 요청별 서류 제출하기

신청 화면이나 **제출 서류**의 **연습자료 ZIP**을 내려받고 압축을 풉니다. 아래에서도 받을 수 있습니다.

- [이하늘 연습자료 ZIP](../examples/ocr_retest_bundle.zip)
- [상담 예시](../examples/ocr_retest/application.txt)
- [자료 안내문](../examples/ocr_retest/README.txt)

`documents` 폴더의 자료는 다음 15종입니다.

| 구분 | 포함한 서류 |
| --- | --- |
| 신분·가족 | 주민등록표등본, 가족관계증명서 |
| 금융·채무 | 계좌통합조회결과, 부채증명서, 예금계좌거래내역 |
| 소득·재직 | 근로소득원천징수영수증, 재직증명서, 건강보험자격득실확인서, 연금산정용가입내역확인서, 스캔 급여명세서 |
| 재산·거주·경위 | 지적전산자료조회결과서, 지방세세목별과세증명서, 보험가입및해약환급금확인, 무상거주확인, 채무발생및생활비진술 |

요청 카드의 종류·기관·계좌·기간을 확인하고 맞는 파일을 제출합니다. **무상거주확인과 채무발생및생활비진술도 빠뜨리지 마세요.** 같은 파일을 여러 번 올려도 다른 종류의 증빙을 대신하지 않습니다.

해당 자료의 요청 카드가 없다면 **제출 서류 → 다른 자료 제출 → 별도 참고 자료**로 올릴 수 있습니다. 제출 후 담당자가 사건에 필요한 자료인지와 내용을 확인합니다.

기관이나 계좌가 미확정이면 담당자가 하늘테스트은행, `TEST-ACCOUNT-SKY-002`, 하늘테스트물류로 확인합니다. 급여소득만 있는 상담에서 사업자등록증이나 매출 자료가 불필요하게 요청되지 않는지도 확인할 수 있습니다.

`optional_error_checks`는 명의·기간 불일치를 시험하는 별도 자료입니다. 정상 흐름을 먼저 확인한 뒤 사용하며 정상 서류와 한꺼번에 제출하지 않습니다. 오류 사유와 재요청이 고객 화면에 전달되고, 올바른 자료를 다시 제출했을 때 이전 이력이 남는지 확인합니다. `manifest.json`과 안내문은 검산용이며 제출할 증빙이 아닙니다.

## 4. 검증과 자동 작성 확인하기

직원은 **자료 검증**에서 명의·기간·범위와 원문 내용을 확인합니다. 필요한 자료의 제출·검토가 끝나면 **사건 개요 → Case Automation**에서 내용 추출, 원문 대조, 계산·쟁점 분석, 1차 문서 자동 작성, AI 문서 검토의 진행 상황을 볼 수 있습니다. 처리 시간은 자료와 로컬 실행 환경에 따라 달라집니다.

**법원 서식**에서는 파일이 생겼는지만 확인하지 말고, **작성본 PDF**의 본문·표·근거별지를 직접 읽습니다. **작성 내용·AI 검토 확인**에서 원문에서 확인한 값, 미확정 항목, 법률 판단 제안을 구별합니다. 잘못된 내용을 보완하면 **새 버전 작성 → AI 문서 재검토**로 이어지고 이전 작성·검토 이력은 보존됩니다.

이하늘 사례에서 비교할 주요 값은 다음과 같습니다.

| 항목 | 확인할 값 |
| --- | --- |
| 월 급여 | 총급여 355만원 − 공제 35만원 = 실수령 320만원 |
| 연간 소득 | 총급여 4,260만원 − 공제 420만원 = 실수령 3,840만원 |
| 채무 | 원금 6,900만원 + 이자 300만원 = 7,200만원 |
| 예금 | 240만원 |
| 실제 월 생활지출 | 160만원 |
| 가족·거주 | 1인가구, 부양가족 없음, 무상거주 |

연금 기준소득 355만원은 실수령액과 다릅니다. 예금 240만원을 생활비로 바꾸어 쓰면 안 되며, ‘급여외 소득 없음’은 무직을 뜻하지 않습니다. 실제 생활지출과 법률상 인정 생계비도 별도로 검토합니다.

자동 검토가 어려운 부분은 사유를 남기고 담당자 확인으로 이어집니다. 원문에서 확인한 사실을 바탕으로 초안을 만들 수 있지만, 검토하지 못한 항목까지 통과했다고 표시해서는 안 됩니다.

## 5. 변호사 검토와 제출 준비 확인하기

변호사 계정에서 **문서·결과**를 열고 작성본 전체, 보완 사유, 제출 조건을 확인합니다. 조건을 충족한 문서는 제출 패키지로 준비하고 변호사가 최종 승인합니다. 자세한 순서는 [문서 검토와 제출 기록](filing-review.md)을 참고하세요.

가상자료에는 실제 주민등록번호·전화번호·서명이 없습니다. 이 항목과 확정하지 않은 법률 판단은 보완 대상으로 남는 것이 정상입니다. 테스트를 끝내기 위해 임의의 실제 정보나 접수증을 만들어 넣지 마세요. 앱은 법원으로 자동 전송하지 않으며, 실제 외부 제출 이후에만 접수증과 제출 기록을 연결합니다.

## 개발자가 다시 확인하는 방법

다음 검사는 원문을 실제로 읽고 작성 문서의 값과 근거를 대조합니다. 실제 고객 사건과 분리된 자료를 사용하며, 기대값은 검사 도구에만 제공하고 추출기에 답으로 전달하지 않습니다.

```powershell
python -X utf8 scripts/audit_document_extraction.py
python -X utf8 scripts/audit_generated_documents.py
```

첫 검사는 문서별 추출 항목과 정확한 원문 인용, 금액 집계, 은행 거래내역 12개월 행을 대조합니다. 두 번째 검사는 앞서 저장한 검사 사건으로 실제 7종 PDF를 만들고 원래 서식의 칸과 근거별지에 값이 보존됐는지 확인합니다. 실제 생성된 진술 내용을 추가로 대조하려면 두 번째 명령에 `--narrative 파일경로`를 붙일 수 있습니다. 이 검사는 AI 최종 승인이나 법원 제출을 대신하지 않습니다.

결과는 `reports/ocr-audit`의 `*-extraction.json`, `*-generated-documents.json`에 남습니다. 같은 폴더의 `generated-visual-review.json`에는 7종 35쪽의 실제 배치 확인과 겹침 수정 결과도 기록했습니다. 이 기록은 로컬에 보관하며 Git에는 포함하지 않습니다. [서류 읽기 안내](ocr.md)와 [문서 내용 정리 안내](document-extraction.md)에서 판독과 항목 해석의 범위·남은 한계를 확인할 수 있습니다. 이 가상자료 검증만으로 모든 기관의 서식이나 실제 사건의 정확도를 보장하지는 않습니다.

개발용 연동 규격은 http://localhost:8000/docs 에서 확인합니다.

## 연습한 사건 정리하기

사건을 삭제해야 할 때만 아래 관리 도구를 사용합니다. 먼저 `scripts/reset_test_case.py 사건ID`로 삭제 범위를 확인합니다. `--apply`를 붙이면 서버가 종료된 상태에서 백업을 만들고 지정한 가상 사건의 원본·작성본·이력·사건별 학습 기록을 정리합니다. 계정, 다른 사건, 공식 법령, 실행 설정은 유지합니다.

정리 결과는 `reports/test-case-reset.json`, 백업은 `.local/backups`에 남습니다. 백업은 현재 사건 검색·학습에 사용되지 않습니다. 계정까지 지우는 전체 초기화 도구는 사건 하나를 정리할 때 사용하지 않습니다. 새 시작 설정은 `.local/start-profile.json`에 저장되므로 재실행해도 예전 시연 사건을 자동으로 만들지 않습니다.
